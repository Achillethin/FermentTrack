# Evolution Spec: fermentation-control-poc → legitimate industrial-control dependency

**For:** a Claude session working in `fermentation-control-poc` directly.
**Origin:** an audit run from FermentTrack (2026-09-17) reproduced the soft-sensor result exactly (R²=0.9835, nRMSE=0.0343) but found it's validated on industrial penicillin fermentation (IndPenSim), not wine — and found MPC is self-validated against its own generating simulator, not a real controller. Full audit: `FermentTrack/docs/DEPENDENCIES.md` (section 3) — read that first.

## Where things actually stand (verified, not asserted)

- Soft sensor (`src/fermentation_poc/models/soft_sensor.py`, RandomForest predicting offline biomass from 5 online sensors) is **legitimately good and reproducible**: live re-run on the cached 100-batch IndPenSim CSV matched the committed metrics exactly, using a proper batch-level holdout (`make_train_test_split`/`make_group_holdout_split`) — no intra-batch leakage.
- **But IndPenSim is industrial penicillin fermentation** (*Penicillium chrysogenum*, fed-batch pharma process) — not wine, not any beverage/food fermentation. `docs/research/04_action_plan.md` itself admits no real wine fermentation dataset with published raw data currently exists. The README's "S10 GO" framing reads as wine-relevant progress; today it's a pharma-domain result only.
- `src/fermentation_poc/control/mpc.py` (correct path — not `control/mpc.py`) self-labels "PAS un MPC de production" — a brute-force grid search over 6 temperature candidates. **Update (2026-09-17 re-check):** `scripts/evaluate_mpc.py` now perturbs `mu_max, Ks_glucose, Ks_fructose, S0, N0` by ±5% across 30 batches (`jitter_params`, added per `docs/research/04_action_plan.md:47-56`, dated after the original audit) — a step beyond pure self-consistency. But it's still the same Monod/Boulton model class generating both the "fixed" and "mpc" conditions, and `tests/test_mpc.py` only checks MPC against its own `MonodBatchSimulator` — no independent model or real data. The core concern (no validation against something the controller wasn't derived from) still holds.
- Package (`fermentation-poc` v0.1.0, `src/`-layout) is clean and installable; `SoftSensor` (`.fit`/`.predict`/`.load`) is a real, narrow, importable class with no trained-model artifact currently checked in.
- FermentTrack's target users (Phase 1: home/micro-producers) log sparse manual measurements a few times per batch. This soft sensor needs dense online multi-sensor streams (substrate, DO₂, pH, temp, volume at short intervals) — a structurally different data shape, not a config change.

## Action items

1. **Fix the headline framing.** Don't present the R²=0.98 result as a wine-fermentation milestone when it's a penicillin-benchmark result. Relabel the S10 milestone explicitly as "industrial soft-sensor feasibility, validated on IndPenSim (pharma benchmark)" and treat wine validation as a separate, still-open milestone.
2. **Close the real data gap — this is the actual bottleneck, not modeling.** Per your own action plan, no public raw wine fermentation dataset exists. (a) Sourcing lab-collected data through a partner winery/oenology lab is external, human, weeks-to-months work — **not agent-executable, do not put this in an autonomous loop.** (b) **Already partially done, don't re-discover it:** `data/external/yeast_soft_sensor/` (Zenodo — K. marxianus, P. pastoris, Y. lipolytica) is already downloaded with baseline metrics already computed at `data/processed/yeast_baseline_metrics.csv` (RandomForest R²=0.58 overall, well below IndPenSim's 0.98). This *is* the lower-fidelity domain-correct alternative called for here — the remaining work is re-running it with the same batch-holdout rigor as IndPenSim and reporting the honest (weaker) numbers, not finding a new dataset. (c) Being explicit that wine is aspirational is a concrete doc edit (safe for a loop); deciding *when* to give up looking for wine data is a judgment call (not safe for a loop).
3. **Replace the MPC baseline.** Implement with `do-mpc` or CasADi, add real actuator/safety constraints, and validate it against a model or dataset it was **not fit to** — e.g. jittered/unseen parameter regimes, injected sensor noise, or (once available) real IndPenSim batches the controller never saw during design. Report closed-loop performance under those conditions specifically; the current self-consistency check should not appear in any results claiming "closed-loop" validation.
4. **Decouple soft sensor from MPC in packaging.** Keep `SoftSensor` as a standalone importable surface (`fermentation_poc.models.soft_sensor.SoftSensor`) so a consumer can depend on the sensor alone without pulling in the unvalidated controller. Don't ship a combined "control" install path until MPC clears item 3.
5. **Define a dense-sensor data contract.** Document exactly which columns, units, and sampling rate the soft sensor expects (grounded in what real industrial rigs actually emit, not just IndPenSim's schema) — this becomes the interface any downstream consumer (e.g. FermentTrack's future industrial-control module) needs to build an ingestion adapter against.
6. **Consider repositioning around methodology, not commodity.** The genuinely interesting, currently-provable claim is "predict a rare/expensive offline measurement from dense online sensors" as a general fermentation soft-sensor pattern — validated today on IndPenSim, wine as an explicit future target. That's a more honest and still valuable pitch than implying wine-readiness now.

## Definition of done (flips FermentTrack's verdict from "don't use yet" on MPC / "use later" on soft sensor)

- **Soft sensor:** validated (comparable R²/nRMSE, same batch-holdout rigor) on a real fermentation-domain dataset — penicillin doesn't count, even a beer/kombucha dataset would meaningfully move the needle before wine data exists.
- **MPC:** rebuilt on a constrained solver (do-mpc/CasADi) and validated closed-loop against a model/dataset it wasn't fit to. Until this lands, no "control recommendation" UI should be built on top of this repo by anyone.
